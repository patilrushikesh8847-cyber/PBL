====================================================================== 1.
PRODUCT VISION AND TARGET USERS
======================================================================

Product: AI Interview Coach Purpose: Help students and early-career job
seekers prepare for campus placements, internships, technical
interviews, HR rounds, coding interviews, and company-specific
interviews through realistic practice and actionable feedback.

Target users: - College students preparing for campus placements. -
Diploma, undergraduate, and postgraduate students. - Internship
applicants and entry-level job seekers. - Users preparing for HR,
behavioral, technical, coding, and aptitude rounds.

Core product promise: Users practise interviews in a structured
environment, receive evidence-based feedback on their answers,
understand weaknesses, and follow a practical improvement plan.

The application is a practice and educational tool. It must not promise
job placement, guarantee interview success, or present AI scoring as an
objective hiring decision.

3. RECOMMENDED TECHNOLOGY STACK
======================================================================

Frontend: - React with Vite. - TypeScript preferred. - Tailwind CSS for
styling. - React Router for navigation. - A maintained form validation
library or typed validation approach. - Recharts for charts when real
data exists. - Accessible reusable components. - Use a maintained
data-fetching strategy with loading, error, and retry states.

Backend: - Python with FastAPI. - Pydantic request/response schemas. -
SQLAlchemy or another maintainable ORM. - Alembic or equivalent database
migrations. - Structured logging and centralized exception handling. -
API versioning, e.g. /api/v1.

Database and authentication: - PostgreSQL, hosted through Supabase or
another managed PostgreSQL provider. - Supabase Auth is the recommended
authentication option. - Enforce user-level authorization in the backend
and, if using Supabase directly, suitable Row Level Security policies. -
Never trust a user_id supplied by the browser; derive identity from the
validated session/token.

AI: - Provider-neutral server-side AI service abstraction. - Use a
configured LLM API for question generation and evaluation. - Model name
and provider must come from server environment configuration, not
hardcoded across the codebase. - Validate AI output against a schema.
Retry safely or return a clear error when output is malformed. - Add
timeouts, bounded retries, rate limits, and usage/cost logging without
logging secrets or full sensitive answers unnecessarily. - Do not rely
on AI for authentication, authorization, or security decisions.

Voice: - Browser speech APIs may be used for optional text-to-speech
where supported. - For speech-to-text, use a configured provider or
supported browser API and clearly communicate browser/device
limitations. - Always retain a text-answer fallback.

File handling: - Validate file type, size, and content for resume
uploads. - Extract PDF/DOCX text server-side using maintained
libraries. - Store uploaded files in private storage; use short-lived
signed access where appropriate. - Do not execute uploaded files.

Coding execution: - Never run user-submitted code directly inside the
main API server or ordinary application container. - Use a dedicated
isolated code-execution service/sandbox with CPU, memory,
execution-time, filesystem, and network limits. - If secure execution
infrastructure is not available, release coding practice in
non-executing mode or with curated output questions; do not fake
execution.

Deployment: - Frontend: Vercel, Netlify, or equivalent. - Backend: a
platform that supports Python/FastAPI. - Database/auth/storage: Supabase
or equivalent. - Configure HTTPS, production environment variables,
migrations, health checks, and logs.

4. USER ROLES AND PERMISSIONS
======================================================================

Role 1: Guest - Can view landing page, product explanation, sample
questions, and public FAQs. - Cannot view private user data or start a
saved interview without signing in, unless a deliberate guest mode is
implemented with clear limits.

Role 2: Student/User - Can manage their own profile. - Can create, run,
view, and delete their own practice sessions, subject to retention
policy. - Can access their own reports, bookmarks, and uploaded
resume. - Cannot access another user’s sessions, profile, files, or
results.

Role 3: Admin (optional after MVP) - Can manage curated question-bank
content and review system health. - Must have explicit role-based
permissions and protected admin routes. - Must not automatically have
unrestricted access to private interview answers or resumes. Any
operational access must be justified, minimized, and audited.

Authorization must be checked server-side for every protected resource.
Hiding a button in the frontend is not authorization.

5. REQUIRED USER JOURNEYS
======================================================================

Journey A — First-time user: 1. Visit landing page. 2. Read what the
product does and its limitations. 3. Register or sign in. 4. Complete
onboarding: education/experience level, target role, preferred interview
categories, and optional goals. 5. Land on dashboard. 6. Start a
practice interview. 7. Select category, difficulty, and question count.
8. Read instructions and privacy notice. 9. Answer each question. 10.
Submit and receive evaluation. 11. View summary, strengths, improvement
areas, and next steps. 12. Save result automatically and return to
history.

Journey B — Returning user: 1. Sign in. 2. View real dashboard
statistics and recent sessions. 3. Resume a saved draft if draft saving
is implemented, or start a new session. 4. View previous interview
feedback. 5. Compare performance over time using comparable scores and
clearly described metrics.

Journey C — Resume-based preparation (P1): 1. Open profile/resume
section. 2. Upload a supported PDF/DOCX file. 3. See file name, size,
upload status, and delete option. 4. Confirm that the file will be
processed for interview preparation. 5. Extract text safely and display
a preview where appropriate. 6. Generate role-relevant questions based
on extracted content. 7. Let the user remove the resume and associated
extracted text.

Journey D — Voice interview (P1): 1. Request microphone permission only
after a clear user action. 2. Show recording state and clear start/stop
controls. 3. Show transcript for review/edit before submission when
feasible. 4. Offer text entry if microphone or speech recognition is
unavailable. 5. Never record in the background or imply that recording
continues after stopping.

7. AI INTERVIEW ENGINE
======================================================================

Implement a modular AI service with separate functions: -
generate_interview_questions(…) - evaluate_answer(…) -
generate_session_summary(…) - generate_improvement_plan(…) - optionally
generate_follow_up_question(…)

Question generation inputs: - Interview category. - Target role and
skill focus if supplied. - User experience/education level. -
Difficulty. - Number of questions. - Optional job description or
resume-derived facts. - Language preference if supported.

Question generation output: - Question ID or stable session
identifier. - Question text. - Category. - Difficulty. - Skills
assessed. - Optional evaluation rubric. - Optional source/grounding
notes for technical factual questions.

Evaluation output must be structured and schema-validated: - Overall
score and score scale. - Dimension-level scores. - What the answer did
well. - Specific gaps or inaccuracies. - Actionable improvements. -
Example structure or illustrative improved answer. - Suggested follow-up
practice. - Confidence/limitations where appropriate.

Suggested evaluation dimensions: For HR/behavioral answers: 1. Relevance
to the question. 2. Structure and clarity (STAR can be suggested when
appropriate). 3. Specificity and evidence/examples. 4. Reflection and
learning. 5. Communication and conciseness.

For technical answers: 1. Conceptual correctness. 2. Completeness. 3.
Reasoning/explanation. 4. Practical application or examples. 5.
Trade-offs and limitations where relevant.

For coding answers (only when coding feature is enabled): 1. Correctness
against tests. 2. Algorithmic approach. 3. Time complexity. 4. Space
complexity. 5. Readability and edge cases.

Scoring rules: - Publish the rubric and explain what each score means. -
Use consistent bounded scores, e.g. 0–100, with documented weighting. -
Do not treat a score as a scientific measure of employability. - Do not
score accent, inferred ethnicity, gender, disability, facial appearance,
or other protected/sensitive traits. - Do not infer personality,
honesty, or mental health from voice/video. - Do not evaluate camera
appearance or emotion. - Communication feedback should focus on
understandable, actionable characteristics of the submitted answer, not
accent discrimination. - Do not invent factual corrections. When unsure,
say the answer needs verification. - A blank or extremely short answer
should receive appropriate feedback, not an arbitrary high score. -
Provide deterministic or repeatable scoring where feasible; record the
rubric/model version used. - Store model/provider name and prompt/rubric
version where useful for debugging and reproducibility, without exposing
internal prompts or sensitive logs to end users. - Never display hidden
chain-of-thought. Provide concise explanations and evidence-based
feedback instead.

AI prompt injection and untrusted input: - Treat resume text, job
descriptions, user answers, and uploaded documents as untrusted content,
not instructions to the AI system. - Explicitly instruct the model to
use such content only as data for the task. - Never let a resume or
answer override system policies, database permissions, or tools. - Do
not pass secrets or unrelated user data to the model. - Bound input
length and sanitize/validate structured output.

AI provider failure: - Handle timeout, rate limit, invalid output, quota
exhaustion, and provider outage. - Display a clear retry option. -
Preserve the user’s submitted answer before requesting evaluation. - Do
not silently return fabricated feedback. - Use curated fallback
questions if question generation fails, and label them as curated
fallback content.

8. DATABASE AND DATA MODEL
======================================================================

Create migrations and indexes for at least the following logical tables.
Adapt exact names to ORM conventions and document them.

1.  profiles

-   id: same identity as auth user ID, primary key.
-   display_name.
-   education_level (optional).
-   field_of_study (optional).
-   experience_level.
-   target_role (optional).
-   preferred_categories (structured or normalized).
-   created_at, updated_at.

2.  interview_sessions

-   id: UUID primary key.
-   user_id: foreign key to auth identity.
-   category.
-   difficulty.
-   target_role (optional).
-   status: draft, in_progress, completed, failed, or abandoned.
-   question_count.
-   overall_score (nullable until evaluation).
-   rubric_version.
-   model_provider/model_name where appropriate.
-   started_at, completed_at, created_at, updated_at.

3.  interview_questions

-   id.
-   session_id.
-   question_text.
-   category.
-   difficulty.
-   skills_assessed.
-   order_index.
-   rubric/metadata when appropriate.
-   created_at.

4.  interview_answers

-   id.
-   session_id.
-   question_id.
-   user_id.
-   answer_text or securely stored transcript reference.
-   evaluation JSON/structured fields.
-   score (nullable).
-   submitted_at, evaluated_at.
-   Include appropriate uniqueness constraints to avoid duplicate
    answers per question where intended.

5.  question_bank

-   id.
-   question_text.
-   category.
-   difficulty.
-   role/skill tags.
-   suggested answer framework or rubric.
-   source/license metadata where relevant.
-   is_published.
-   created_at, updated_at.

6.  bookmarks (P1)

-   user_id, question_id, created_at.
-   Unique constraint on user_id + question_id.

7.  resumes (P1)

-   id, user_id, private storage key, original filename, file type, file
    size, processing status, extracted text reference or protected text,
    created_at.
-   Never make private resume storage publicly readable.

8.  usage_events (optional, privacy-minimized)

-   event type, user ID where necessary, timestamp, minimal metadata for
    usage/cost limits.
-   Do not store unnecessary sensitive content.

Data model requirements: - Use UUIDs or other non-guessable
identifiers. - Foreign keys, indexes, constraints, and cascading
behavior must be intentional. - Define data retention and deletion
behavior. - Use UTC timestamps in storage and localize in UI. - Never
use client-supplied user IDs as proof of authorization. - Do not store
API keys, raw passwords, or unnecessary sensitive information. - Avoid
storing full AI prompts/responses in production logs unless necessary,
access-controlled, redacted, and retention-limited.

10. SECURITY, PRIVACY, AND RESPONSIBLE AI
======================================================================

Security is a release requirement, not an optional enhancement.

Authentication and authorization: - Use a maintained authentication
provider. - Verify JWT/session tokens correctly, including
issuer/audience and expiry as applicable. - Enforce ownership checks for
every session, answer, resume, report, and profile. - Add database Row
Level Security policies if applicable and test them. - Protect admin
routes and secrets. - Use secure cookie/token handling according to the
chosen auth architecture.

Secrets: - Store secrets in environment variables or a secret manager. -
Include .env.example with placeholders only. - Add .env, local
databases, private uploads, and secret files to .gitignore. - Never
expose service-role keys or LLM keys to the frontend. - Rotate any key
accidentally committed.

Input and web security: - Validate content types and input length. -
Prevent SQL injection using parameterized ORM queries. - Escape
user-provided content in the UI. - Mitigate XSS, CSRF where relevant,
SSRF in URL-fetching features, and unsafe file uploads. - Apply request
limits and rate limiting. - Avoid arbitrary URL fetching from
user-supplied job descriptions unless a safe, restricted fetcher is
designed. - Set appropriate security headers.

Privacy: - Publish a clear privacy notice describing what is collected,
why, where it is stored, and which AI/speech providers receive it. -
Obtain informed permission before microphone use or uploading resumes. -
Allow users to delete resumes and their own interview history. -
Implement account deletion and define deletion of linked data and
storage objects. - Do not sell or expose personal interview answers. -
Minimize retention of raw audio. Prefer not storing audio unless a clear
feature requires it and consent is explicit. - Do not record video or
infer emotion/identity. Video analysis is out of scope for MVP. -
Provide an accessible way to report an issue or request help. - Do not
claim legal compliance without an actual review of applicable law and
provider terms.

Responsible AI: - Make clear that feedback is AI-generated and may be
wrong. - Avoid discriminatory or protected-trait scoring. - Do not use
the app as an automated employment selection system. - Give useful
explanations and suggestions rather than unsupported judgments. - Test
across varied writing styles and language proficiency. - Provide
human-readable error and correction paths.

======================================================================
11. NON-FUNCTIONAL REQUIREMENTS
======================================================================

Performance: - Set practical response-time targets and measure them. -
Avoid unnecessary frontend bundles and repeated database queries. -
Paginate histories and question lists. - Use timeouts for all external
service calls. - Stream AI responses only if the UX and error handling
support it; otherwise return validated structured results.

Reliability: - Graceful handling of network loss and external provider
failure. - Preserve submitted answers before evaluation where
possible. - Health/readiness endpoints. - Database migration and
backup/restore documentation. - No silent data loss.

Scalability: - Stateless API design where practical. - Connection
pooling. - Rate limiting and usage quotas. - Async/background jobs for
longer tasks when needed. - Do not build complex microservices before
the MVP requires them.

Maintainability: - Typed schemas. - Clear separation of frontend,
backend, database, and AI provider layers. - Consistent naming and
formatting. - Linting and automated tests. - Architecture decisions
documented. - No giant single-file application implementation.

Accessibility and usability: - Keyboard access and visible focus. -
Responsive layout. - Clear labels and validation. - Avoid reliance on
color alone. - Support zoom and reduced motion. - Simple language and
actionable feedback.

======================================================================
12. TESTING AND ACCEPTANCE CRITERIA
======================================================================

Testing layers: - Unit tests for validation, scoring/rubric helpers, and
business logic. - API integration tests. - Database/authorization
tests. - Frontend component and flow tests. - End-to-end tests for
critical user journeys. - Security tests for cross-user data access and
malformed input. - Build/lint/type checks in CI. - Manual smoke-test
checklist.

Minimum acceptance criteria: 1. A user can register/sign in and sign
out. 2. An unauthenticated user cannot access private API data. 3. User
A cannot read, modify, or delete User B’s profile, interview, answers,
report, or resume. 4. The user can create an interview session with
valid options. 5. Questions are returned from the configured AI service
or clearly labelled curated fallback. 6. The user can submit an answer
and it is persisted. 7. Evaluation returns schema-valid feedback and a
score based on the documented rubric. 8. AI failure produces an
understandable error and does not erase the answer. 9. Completed
interviews appear in history after refresh and a new login. 10.
Dashboard metrics are computed from actual records. 11. Empty, loading,
success, and error states are present on core pages. 12. UI works at
common mobile, tablet, and desktop widths. 13. Invalid input and
oversized requests are rejected safely. 14. Rate limits or usage
controls protect expensive endpoints. 15. Secrets do not appear in built
frontend assets, Git history, or logs. 16. Database migrations can
create a fresh database. 17. Automated tests pass in documented local/CI
conditions. 18. Production build succeeds. 19. .env.example and README
are complete. 20. Known limitations and incomplete features are
documented honestly.

Do not claim “production-ready” based only on a successful frontend
build. Security, deployment configuration, operational monitoring, and
realistic end-to-end testing still need verification.

Important: No single AI model can guarantee the entire application is
complete, secure, and deployable in one prompt. A model generates and
edits code; the development environment, credentials, runtime tests, and
human verification determine whether the product actually works.

Recommended responsibility split:

A. Strong coding agent/model with repository access Best for: - Auditing
the codebase. - Creating architecture and implementation plan. - Editing
multiple files. - Implementing React/TypeScript frontend and FastAPI
backend. - Creating database schema/migrations. - Running tests, reading
stack traces, and fixing integration bugs. - Updating documentation and
completion matrix. Requirement files: PROJECT_PLAN.md, frontend/backend
source, migrations, tests, README, REQUIREMENTS_TRACEABILITY.md.
Completion test: It must run commands in the actual repository and show
test/build results. A text-only answer is not proof of completion.

B. Reasoning/review model Best for: - Reviewing architecture and
requirements coverage. - Threat modelling and authorization review. -
Checking edge cases and data model design. - Reviewing AI evaluation
rubrics for fairness and clarity. - Auditing test coverage and
deployment readiness. Requirement files: docs/security-and-privacy.md,
docs/architecture.md, docs/test-plan.md, REQUIREMENTS_TRACEABILITY.md.
Completion test: It should identify concrete files, endpoints, risks,
and missing tests, not just say “looks good.”

C. AI model/API used inside the application Best for: - Generating
interview questions. - Evaluating answers against a defined rubric. -
Creating summaries and practice plans. - Optional resume/JD-based
personalization. Requirement files: backend/app/services/ai/, evaluation
schemas/prompts, model/provider configuration. Completion test: Validate
structured outputs and test real API calls with representative inputs,
malformed outputs, timeouts, and quota errors.

D. Speech-to-text/text-to-speech service Best for: - Optional voice
practice. Requirement files: voice UI, speech service adapter,

deployment checklist, secrets manager/hosting settings, release

recorded checklist.

repository editing and terminal/test execution for implementation. - Use

model does not build the application itself. - Do not choose a model
solely by brand or benchmark. Verify repository access, tool support,
